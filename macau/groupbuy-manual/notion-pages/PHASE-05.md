## STEP-12 · 상점 확인 & 상점명 변경

이번 공구를 담을 상점(판매 채널)을 확인하고, 상점명을 이번 건에 맞게 변경한다.

**목적**
- 이번 공구를 담을 상점(판매 채널)을 확인하고, 직전 공구명이 남아 있지 않도록 상점명을 이번 건에 맞게 변경한다.

**담당**
- 메인: 김용성
- ⚙️ 보완(확인필요): 상점 운영 권한 보유자 — 선임이 기본 틀을 잡아두는 구조와 동일한지 확인

**절차**
1. STEP-11(요금표 인플 전달) 완료 확인 — 요금표가 인플에게 전달되어 판매 셋업 단계로 넘어온 상태에서 시작한다.
2. 이번 공구를 담을 상점(판매 채널) 접속 → **사용할 상점 확인**.
3. 상점 상태 점검 — 활성 여부, 연결 정상 여부(노출/링크가 정상 작동하는지) 확인.
4. **상점명을 이번 공구에 맞게 변경** — 직전 공구의 이름이 남아 있으면 이번 건 정보로 교체.
5. 변경 후 상점명·노출 상태를 다시 한번 확인하고 다음 단계(STEP-13 판매코드 생성)로 인계.

<callout icon="⚠️" color="red_bg">
	**직전 공구명이 그대로 남으면 사고** 상점명을 안 바꾸면 고객이 이전 공구 상점명/정보로 인식하게 되어 혼선·CS로 직결된다. 상점명 변경은 빠뜨리지 말 것.
</callout>

<callout icon="⚙️" color="yellow_bg">
	**보완(확인필요)** 상점 플랫폼 정확히 확정(Wix? 자사몰?) — 현재 Wix MCP 연결 상태. 확정 후 접속 경로·메뉴 위치를 본 절차에 보강할 것. 또한 상점과 판매코드·판매 링크가 어떻게 연결되는지(상점 변경이 코드에 영향 주는지) 확정 필요 — STEP-13와의 선후 관계 점검.
</callout>

- 상점 **상태(활성)·연결 정상 여부**를 반드시 확인 — 비활성/링크 깨짐 상태로 다음 단계 진행 시 오픈 직전 발견되면 대응 시간이 부족하다.

**핵심 용어**: 상점 — 이번 공구를 담아 판매하는 판매 채널(상점), 건마다 이름을 바꿔 재사용 · 판매코드 — 상점에 연결되는 판매 식별 코드(다음 단계 STEP-13에서 생성·검증)

**관련 문서**: STEP-11 요금표 인플 전달(선행) · STEP-13 판매코드 생성·검증·전달(다음) · PHASE 05 판매 셋업 · Janda 판매 사이트 & 스프레드시트 운영

## STEP-13 · 판매코드 생성·검증·전달

이번 공구용 판매(상품) 코드를 만들고, 코드 ↔ 상품·가격·링크 연결이 정상 동작하는지 검증한 뒤 인플에게 전달한다.

**목적**
- 이번 공구용 판매(상품) 코드를 만들고, 코드 ↔ 상품·가격·링크 연결이 정상 동작하는지 검증한 뒤 인플에게 전달한다.

**담당**
- 메인: 김용성, 정민님
- 검수: 김용성 (전달 전 클릭 테스트)

<callout icon="⚙️" color="yellow_bg">
	**보완(확인필요)** 판매코드 발급 권한·플랫폼(상점 시스템 기준)이 선임 셋업인지 본인 작업인지 사내 확정 필요. 기존 JBS 일정배치는 "보통 선임이 기본 틀을 잡아둠"이었음 — 판매코드도 동일 분담인지 확인.
</callout>

**절차**
1. 선행 확인: STEP-12에서 이번 공구용 상점이 준비되고 상점명이 이번 건에 맞게 변경되어 있는지 확인.
2. 선행 확인: 요금표가 확정되어 인플에게 전달된 상태인지 확인(STEP-11) — 코드에 연결할 가격의 근거.
3. 판매(상품) 판매코드 생성.
4. 이상 여부 확인 — 코드 ↔ 상품 매핑이 정상인지 (이번 공구 상품과 코드가 맞물리는지).
5. 이상 여부 확인 — 코드 ↔ 가격이 정상인지 (요금표 확정가와 일치하는지).
6. 이상 여부 확인 — 코드 ↔ 링크가 정상인지.
7. **실제 클릭 테스트** — 코드/링크를 직접 눌러 정상 판매 페이지로 이동하는지, 표시 가격이 요금표와 같은지 눈으로 확인.
8. 이상 없음 확인 후 인플에게 판매코드 전달.

<callout icon="⚙️" color="yellow_bg">
	**보완(확인필요)** 판매코드 생성 위치·발급 절차(상점 플랫폼 기준)의 구체 단계는 사내 확정 후 본문 보강.
</callout>

<callout icon="⚠️" color="red_bg">
	**코드 연결 오류 = 오픈 직후 매출 직결 손실** 판매코드의 상품·가격·링크 연결 오류는 오픈 직후 매출 손실로 곧장 이어진다. 눈으로 매핑만 확인하지 말고 반드시 실제 클릭 테스트로 정상 페이지 도달·정상 가격 노출까지 검증한 뒤 인플에게 전달한다.
</callout>

- 코드에 연결되는 가격은 STEP-11에서 확정된 요금표와 **반드시 일치**시킬 것 — 오기입 시 공구 오픈 후 정정 불가에 가까운 클레임으로 번짐.
- 이전 공구의 코드·링크를 그대로 재사용하지 말 것(이전 건으로 연결되는 사고 방지). 이번 공구 상점 기준으로 새로 발급.

**핵심 용어**: 판매코드 — 판매(상품)에 부여되는 코드, 상품·가격·링크와 연결되며 인플에게 전달됨 · 상점 — 이번 공구 판매가 걸리는 판매 단위(STEP-12에서 상점명 변경) · JBS — Jungle Booking System, 품목관리·일정배치 등 판매 셋업 시스템 · KOL — 공구를 진행하는 인플루언서(코드 전달 대상)

**관련 문서**: Jungle Booking system 원본 · Janda 판매 사이트 & 스프레드시트 운영 · PHASE 05 판매 셋업

## STEP-14 · 상세페이지 제작 & 셋팅

최종 구성 노션(SoT)을 근거로 상품별 상세페이지를 제작하고, 품목 누락·가격 오기입을 검수한 뒤 상점에 셋팅·연결한다.

**목적**
- 최종 구성 노션(SoT)을 근거로 상품별 상세페이지를 제작하고, 품목 누락·가격 오기입을 검수한 뒤 상점에 셋팅·연결한다.

**담당**
- 메인: 김용성
- 검수 협업: 정민님
- 수정 요청: 팀장님

**절차**
1. **자체 편집기로 상세페이지 제작** → 상품별 themed 산출물(예: galaxy-macau, lisboa-palace, selectum-noa).
2. **최종 구성 노션(SoT) 기준으로 사실 일치 확인**: 가격 · 포함/불포함 · 유의사항.
3. **각 품목이 빠짐없이 첨부됐는지 순서대로 확인** (CS 폭발 방지 필수 체크).
4. 내용 정확성 재확인: 가격, 일정, 포함 내역 — 특히 후킹가와 상세페이지 가격 불일치 여부.
5. 문제 발견 시 팀장님께 수정 요청 → 수정 완료 후 재확인.
6. **상점에 상세페이지 셋팅·연결**.
7. 셋팅 후 실제 페이지에서 표시 확인 (노션 원문과 최종 대조).

<callout icon="⚠️" color="red_bg">
	**품목 누락 = 오픈 후 CS 폭발** 상세페이지에 품목이 하나라도 빠지면 오픈 후 CS가 폭발한다. 공구 시작 전 반드시 100% 체크할 것.
</callout>

<callout icon="⚠️" color="red_bg">
	**자동저장이 소스 텍스트 편집을 덮어쓸 수 있음** 편집기의 자동저장(window.name)이 소스 텍스트 직접 편집을 덮어쓸 수 있다. 소스 텍스트를 직접 수정할 때는 라이브 동기화에 주의한다.
</callout>

- **가격 오기입 특히 주의** — 후킹가와 상세페이지 가격이 불일치하면 고객 혼란·클레임으로 직결.
- **가격·포함/불포함·유의사항은 반드시 노션(SoT)을 기준**으로 한다. 상세페이지가 SoT이 아니므로, 불일치 시 노션을 우선으로 정정.

<callout icon="⚙️" color="yellow_bg">
	**보완(확인필요)** 상점에 상세페이지를 연결하는 구체 셋팅 경로·연동 방식은 신규 단계라 근거 미확보 → 실무 확인 후 보강.
</callout>

**핵심 용어**: 상세페이지 — 상품 상세 설명 페이지(자체 편집기로 themed 제작) · 상점 — 상세페이지를 셋팅·연결하는 판매 플랫폼 · 후킹가 — 고객을 유인하는 최저 가격

**관련 문서**: 상세페이지 원본 · 마카오 패키지 핵심 정보 · PHASE 05 판매 셋업

## STEP-15 · 품목·재고 셋팅 (데일리 제외)

JBS에 판매 품목·일정을 등록하고, 항공 모객현황·호텔 SCM 실재고와 대조해 재고를 맞춘다. 데일리(매일출발)는 이번 재고 셋업에서 제외한다.

**목적**
- JBS에 판매 품목·일정을 등록하고, 항공 모객현황·호텔 SCM 실재고와 대조해 재고를 맞춘다. **데일리(매일출발)는 이번 재고 셋업에서 제외한다.**

**담당**
- 메인: 김용성, 정민님

**절차**

### 1. JBS 품목·일정 등록
1. JBS 접속: [jungle.booking.stayjanda.cloud]([내부 시스템 주소 삭제])
2. 주요 메뉴 확인
	- **품목관리** — 시스템에 등록된 상품 목록
	- **일정배치** — 날짜별 재고 수량 입력 (주 작업 공간)
	- **카테고리 설정**
3. 일정배치 탭에서 각 상품 일정 세팅 (재고 수량 입력). 일정배치는 보통 선임이 기본 틀을 잡아놓음. 내가 해야 하는 부분은 재고가 호텔 실재고와 일치하는지 확인·수정.

### 2. 항공 모객현황 확인 (확정 가능 일정만 남기기)
4. **에어마카오** — 에어마카오 모객현황 구글 스프레드 확인.
5. **에어부산** — 에어부산 단톡방에 확정 가능 여부 요청.

### 3. 호텔 SCM 객실 가용 확인
6. **갤럭시(안다즈/브로드웨이)** — 갤럭시 담당자님에게 SCM 객실 가용 확인.
7. **리스보아** — 리스보아 담당 이사님에게 SCM 객실 가용 확인.
8. 호텔 부킹 사이트에서 여행 날짜별로 어떤 객실이 남아있는지 직접 파악.

### 4. JBS 재고 ↔ 실재고 일치화
9. JBS 재고와 호텔/항공 실재고가 불일치하면 → **즉시 JBS에서 해당 일정 재고 수정**.
10. 가용 불가 일정은 JBS에서 즉시 제거.
11. **데일리(일별 재고)는 반드시 제외** 후 세팅 완료.
12. 확정 가능 일정만 JBS 상점 정보에 반영.

### 5. 상세페이지 품목 재확인 (CS 폭발 방지)
13. 상세페이지 각 품목 첨부 여부를 순서대로 확인 (누락 없는지).
14. 내용 정확성 재확인 (가격·일정·포함 내역, 후킹가와 상세페이지 가격 일치).
15. 문제 발견 시 팀장님께 수정 요청 → 수정 완료 후 재확인.

### 주요 링크
- **JBS 접속**: [jungle.booking.stayjanda.cloud]([내부 시스템 주소 삭제])
- **에어마카오 모객현황 스프레드**: [구글 스프레드시트]([내부 링크 삭제])
- **마카오 호텔 부킹 사이트(SCM)**: [shijicloud SCM]([내부 시스템 주소 삭제])

### 호텔 투숙 규정 (재고 셋업·예약 세팅 시 필수 확인)

**안다즈 마카오**
- 성인 3명 이상 → Extra Bed 자동 발생 → 추가 비용 발생 (원하지 않아도 발생).
- 성인 2 + 소인 2 → 추가 요금 없음.

안다즈 예약 시 주의:
- 호텔 시스템에서 성인 3 입력 **불가** → 성인 2 + 소인 1로 조회 후 예약.
- Extra Bed 발생 시 → **갤럭시 어드민으로 이메일 발송** 필수 (Extra Bed request).
- 안다즈 Admin 있으나 취소·변경 불가 (우리는 예약만 가능).

안다즈 물량 부족 시:
1. 갤럭시 담당자님께 추가 물량 요청 → 가능/불가 확인.
2. 불가 시 → 고객 날짜 변경 or 호텔 변경 안내.

**브로드웨이 마카오**
- 성인 2 + 소인 1 → MAX (엑스트라베드 공간 없음).
- 성인 3명 → 객실 2개 필요.

<callout icon="⚠️" color="red_bg">
	**브로드웨이 인원 안내** 성인 5명이면 객실 2~3개 필요 — 고객에게 사전 안내 필수.
</callout>

### 호텔 예약 결제 정보 (예약 확정 시 사용)
- (결제카드 등 자격증명은 사내 보안노트 별도 — 담당자에게 요청)

<callout icon="⚠️" color="red_bg">
	**결제 금액 확인** 결제 금액(MOP)이 공구 스프레드 금액과 일치하는지 반드시 확인 후 결제.
</callout>

<callout icon="⚠️" color="red_bg">
	**데일리 제외** JBS 세팅 시 데일리(일별)는 반드시 제외 → 포함하면 오류 발생.
</callout>

<callout icon="⚙️" color="yellow_bg">
	**보완(확인필요)** "데일리 빼기"의 정확한 정의(어떤 품목/옵션이 데일리에 해당하는지, 제외 기준) — 백업 원본엔 "데일리=일별 재고, 포함 시 오류"까지만 기록됨. 선임에게 제외 판단 기준 확인 후 보강.
</callout>

<callout icon="⚠️" color="red_bg">
	**오버부킹·CS 폭발 직결** SCM·모객현황 확인 없이 JBS 세팅 금지 → 오버부킹 시 전액 보상 책임. 호텔 측 시스템에서 특정 날짜 객실(예: 트윈베드) 예약 불가인데 JBS에서 해당 재고를 제거하지 않으면 → 고객이 결제 후 "왜 방 예약이 안 되냐" 클레임 발생. 가용 불가 일정은 즉시 JBS에서 제거(고객 클레임 직결).
</callout>

- 에어마카오와 에어부산 확인 방법이 다름(시트 vs 단톡방) — 채널 혼동 주의.
- 상세페이지 품목 누락 = 오픈 후 CS 폭발 → 공구 시작 전 반드시 100% 체크.
- 가격 오기입 특히 주의 — 후킹가와 상세페이지 가격 불일치 시 고객 혼란.

**핵심 용어**: JBS — Jungle Booking System, 판매 페이지·재고 세팅 시스템 · SCM — 호텔 객실 재고 관리 채널 · 데일리 — 매일출발(일별) 상품/재고, 이번 재고 셋업에서 제외 · 상점 — 판매 품목·일정이 노출되는 판매 페이지 · 상세페이지 — 상품 상세 설명 페이지 · 후킹가 — 고객을 유인하는 최저 가격

**관련 문서**: Jungle Booking system · Janda 판매 사이트 & 스프레드시트 운영 · SCM 부킹 조회 방법 · 고객 예약 확정 프로세스 · 마카오 패키지 핵심 정보 · (결제카드 등 자격증명은 사내 보안노트 별도 — 담당자에게 요청) · PHASE 05 판매 셋업

## STEP-16 · 인플 구매 테스트 & 히든 공개 결정

인플이 실제로 결제 직전까지 구매 흐름을 밟아보게 해 이상이 없는지 검증하고, 오픈 시각까지 상점을 히든으로 둘지 결정한다.

**목적**
- 인플이 실제로 결제 직전까지 구매 흐름을 밟아보게 해 이상이 없는지 검증하고, 오픈 시각까지 상점을 히든으로 둘지 결정한다.

**담당**
- 메인: 김용성
- 협업: 정민
- 상세페이지 수정: 팀장님 (문제 발견 시 요청)

**절차**
1. STEP-15(품목·재고 셋팅·데일리 빼기) 완료 상태 확인 — 실제 구매 테스트가 가능한지 점검.
2. **상세페이지 최종 QA** (구매 테스트 직전): 각 품목이 빠짐없이 첨부됐는지 순서대로 확인, 가격·일정·포함 내역 정확성 재확인 (CS 폭발 방지용 필수 체크).
3. 인플에게 **구매 테스트** 안내 — 상점에 들어가 결제 직전까지 흐름을 밟아보도록 요청.
4. 테스트 결과 이상 없는지 확인 — 품목·재고·옵션·금액 표시, 후킹가와 상세페이지 가격 일치 여부.
5. 문제 발견 시 팀장님께 상세페이지 수정 요청 → 수정 완료 후 재확인.
6. (테스트 시 JBS 예약 메시지가 정상 발송되는지 함께 확인 가능 — 본격 템플릿 교체는 STEP-17.)
7. **히든 vs 공개 결정**: 오픈 시각 전까지 히든 상태로 두고, 오픈 시각에 맞춰 공개하도록 셋업.
8. 상점 **휴무 필요 여부** 판단.

<callout icon="💡" color="gray_bg">
	**할 일 (산출물)** 상세페이지 품목·가격 최종 QA 통과 / 인플 구매 테스트 통과 확인 / 오픈 공개 방식(히든→오픈 시각 공개) 및 상점 휴무 여부 결정.
</callout>

<callout icon="⚠️" color="red_bg">
	**오픈 전 노출 사고** 히든 처리를 빠뜨리면 오픈 시각 전에 상품이 외부에 노출될 수 있다. 테스트 직후 반드시 상점을 히든 상태로 되돌리고, 오픈 시각에 공개하도록 셋업했는지 재확인한다.
</callout>

- **품목 누락 = 오픈 후 CS 폭발** → 구매 테스트 전 반드시 100% 체크.
- 가격 오기입 특히 주의 — 후킹가와 상세페이지 가격이 불일치하면 고객 혼란.

<callout icon="⚙️" color="yellow_bg">
	**보완(확인필요)** 구매 테스트 안내 시 인플에게 전달하는 멘트·범위(실결제 여부, 결제 직전 중단 지점 등) 표준화 — 근거 없는 수치/멘트 임의 생성 금지.
</callout>

**핵심 용어**: 상점 — 인플별 판매가 열리는 상점(판매 페이지) · 히든 — 오픈 시각 전까지 상점·상품을 외부에 노출하지 않는 상태 · 상세페이지 — 상품 상세 설명 페이지 · 후킹가 — 고객을 유인하는 최저 가격 · JBS — Jungle Booking System, 판매 페이지 세팅 시스템

## STEP-17 · 예약 발신 템플릿 설정 (구글폼·예약메시지)

공구별 여권 수집용 구글폼을 신규 생성하고, JBS 예약 메시지 템플릿의 폼 링크를 새 폼으로 교체·활성화해 오픈 직후 구매 → 예약정보 입력 동선을 미리 완성한다.

**목적**
- 공구별 여권 수집용 구글폼을 신규 생성하고, JBS 예약 메시지 템플릿의 폼 링크를 새 폼으로 교체·활성화해 오픈 직후 구매 → 예약정보 입력 동선을 미리 완성한다.

**담당**
- 메인: 김용성

**절차**
1. **여권 정보 입력용 구글폼 신규 생성** — 이번 공구 전용으로 새로 만든다. 이전 공구 폼을 재사용하지 않는다.
2. **수집 필수항목 고정** — 후속 단계(STEP-26 여권정보 미입력 문자 · STEP-27 PNR APIS 제작)에서 쓰는 항목 기준으로 폼 항목을 구성한다.
3. **JBS 예약 메시지 템플릿 접속** — JBS(jungle.booking.stayjanda.cloud)에서 예약 메시지 템플릿을 연다.
4. **템플릿 내 구글폼 링크를 새 폼으로 교체** — 1에서 만든 신규 폼 URL로 기존 링크를 덮어쓴다.
5. **기능 켜기(활성화) 확인** — 메시지 발송 기능이 활성 상태인지 점검한다.
6. **테스트 예약으로 정상 발송 확인** — 구매 완료 → 예약 메시지 발신 → 신규 구글폼으로 연결되는지 한 번 끝까지 돌려본다.

<callout icon="⚙️" color="yellow_bg">
	**보완(확인필요)** 이번 공구의 구체 필수항목 목록(여권 영문명·여권번호·생년월일·국적 등)을 오픈 전에 확정해 고정.
</callout>

<callout icon="⚠️" color="red_bg">
	**폼 링크 교체 누락 = 대형 CS** 기존 폼 링크를 그대로 두면 이전 공구 폼으로 여권이 수집된다. 새 공구마다 반드시 신규 폼을 생성하고 JBS 템플릿 링크를 교체할 것.
</callout>

- 현재 사용 중인 폼 링크(참고):
	- 마카오 일반: [[내부 링크 삭제]]([내부 링크 삭제])
	- 마카오 리스보아: [[내부 링크 삭제]]([내부 링크 삭제])
- 여기서 수집한 예약정보가 이후 단계의 기준 데이터가 된다. 수집 필수항목이 빠지면 STEP-26 추출과 STEP-27 APIS 제작에서 누락이 그대로 이어진다. 필수항목은 오픈 전에 고정하고, 오픈 후 임의 변경은 피한다.

**핵심 용어**: JBS — Jungle Booking System, 판매 페이지·예약 메시지 세팅 시스템 · 구글폼 — 공구별 여권·예약정보 수집 폼 · 바우처 — 고객 예약 확정·발권의 근거가 되는 수집 정보 흐름과 연결
